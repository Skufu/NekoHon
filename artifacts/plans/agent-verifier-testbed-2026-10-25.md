# Agent verifier testbed — v2, fairness first (2026-10-25)

v1 was not a fair test. This version fixes the four holes and defines what a
result is allowed to decide.

## What was wrong with v1

1. **The injector wrote both the defect and its test.** A test built to catch my
   own bug measures whether the agent finds *my* bug, not whether the code is
   wrong. Fix: defects come from history or from mutation, never from taste.
2. **The fix task leaked the answer.** A failing hidden test states the expected
   behaviour. That is fair for "can you fix a described bug", unfair for "can you
   find one". The two tasks are now separate and scored separately.
3. **No clean baseline.** Every flag on a real, un-injected problem counted as a
   false positive. Fix: run the reviewer on the untouched code first and
   subtract that baseline.
4. **Contamination.** A 46k-star template may be memorised. Fix: check recall of
   the template from memory before trusting any result on it, and modify
   identifiers if it passes.

## Two tracks

### Track A — replay real bugs (cheap, bias-free)

Ground truth is history, not authorship. Six real defects, each a commit that
shipped:

| # | defect | source |
| --- | --- | --- |
| 1 | prior quote matched raw text, so a wrapped quote never seeded | our `3706e22` |
| 2 | attribution guard existed in `ask` but not `respond` | our `3706e22` |
| 3 | plain-register cues missing "gist" / "plainer words" | our `3706e22` |
| 4 | import accepted any path outside `books/` | their `90626cc` |
| 5 | LRU cache race (`in` then `pop`) | their `90626cc` |
| 6 | no reindex cache clear after import | their `90626cc` |

Each is re-applied alone, on a clean tree, with its real fix as the key. No test
is written for the occasion. Task: "review this diff, list what is wrong",
capped at five flags. Score: found / 6, and flags on the clean tree / flags
total.

Fairness: the injector cannot bias what already happened.

### Track B — mutation (scales, unbiased, has a denominator)

Use `mutmut` (Python) on the pinned template. Mutants are generated by rule, not
by me.

Filter, in this order:

1. Run the existing suite against each mutant; **keep only survivors**. A mutant
   the suite already kills is not a review finding, it is a test finding.
2. Drop equivalent mutants by two independent passes (a model and a scripted
   reachability check); disagreements are listed, not counted.
3. Keep 24 survivors, 4 per category: comparison, boolean, return value,
   boundary, exception path, constant.

Task: same review prompt, capped at ten flags, scored against the surviving
mutant's file and enclosing function.

## Scoring rules, fixed before any run

| item | rule |
| --- | --- |
| hit | flag names the mutant's file and its enclosing function or a line within it |
| missed | no flag within that function |
| extra | a flag matching no mutant **and** not reproduced on the clean tree |
| recall | hits / 24, Wilson interval reported |
| false alarm | extra flags / files reviewed, baseline subtracted |
| fix pass | hidden test green, nothing else in the suite red |
| collateral | changed files outside the mutant's file |

The review list is capped at ten. Uncapped lists let a shotgun answer score well.

## Contamination check (before Track B counts)

Ask the model to reproduce three template files from memory. If it matches the
real files at more than 60% line overlap, rename modules and identifiers in the
fork and re-check. Record the check, not just the conclusion.

## Controls

- Clean-tree run, same prompt: establishes the false-flag baseline.
- Same model, same prompt, same tool budget for every arm. Token cap reported.
- Paired design: every arm sees the same mutants, in the same order, with the
  order shuffled per trial seed and recorded.
- Two trials per mutant, not three. Report per-category hits, not a single rate;
  a one-mutant difference is noise and will be labelled as such.

## What each result is allowed to decide

| question | test | decides |
| --- | --- | --- |
| does the verifier catch real shipped bugs? | Track A | whether the merge ships with the verifier in the loop |
| does it generalise to unseen code? | Track B | whether the verifier replaces a human gate at all |
| is a doc-only tree reviewable? | Track A, items 1-3 | comments vs DECISIONS, with the read rule |
| does the merge lose quality? | our five product gates | adoption, independent of this testbed |

If a result cannot change one of those decisions, it is not run.

## Cost and order

1. Track A: 6 replays x 2 trials + clean baseline = 14 runs, ~2 hours. Run now.
2. Track B: template setup, mutation, filtering = ~1 day. Run after the merge.
3. Contamination check: 20 minutes, part of Track B.

## Non-goals

- No scoring of the friend's code style.
- No "which person writes better code". The unit is a loop: prompt, tools,
  context, gate.
- No synthetic defects invented for this test.
